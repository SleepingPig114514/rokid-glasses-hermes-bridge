# Rokid 眼镜端行为实测记录

本文记录 `rokid-bridge` 插件在真实设备（Rokid glasses + RCS 云端桥）上反复实测
确认的协议行为。这些行为不在官方协议文档里，是适配器多处防御性设计的依据，
改动 `adapter.py` 出站逻辑前请先读本文。

实测环境：`wss://rcs.rokid.com/claw/ws/link`，固件/云桥版本以 2026-10 为准。

## 1. done 帧之后，设备不再接受任何后续帧

- 现象：请求一旦收到 `event:"done"` / `is_finish:true`，眼镜立刻退出"等待回复"
  状态；此后同一 `requestId` 再推的任何 `message` 帧（包括重开的新 `done` 链、
  伪造的 agent 主动推送 `push-*`）设备端完全无显示。
- 结论：`done` 是设备侧的单行道。**迟到的真实答案必须在请求保持打开时才可见**。
- 设计影响：
  - 心跳（"…"占位帧）永不发 done，只发非终止 message 帧。
  - 插话排队时，前一个答案到达后**不发 done**，等排队的第二个答案到达才收尾；
    两个答案在同一气泡内以换行分隔。
  - 网关 mid-turn 插话评论（`_interim_send`）只推正文、不发 done。
  - "提前 22 秒主动关单 + 迟到答案改推送"的两段式方案曾实测，被本条否决。

## 2. 一次唤醒会话内，所有消息共用同一个 requestId

- 现象：日志实测所有入站帧 `requestId` 均为同一值（如 1791528527878），并非
  每条消息一个新 ID。唤醒词进入智能体后，用户连续多轮说话都是同一个 ID。
- 结论：`requestId` 不能当 turn ID 用；"新一轮对话"与"插话"在传输层无法靠
  ID 区分，只能靠适配器自己的轮次状态（`_turn_active`）判断。

## 3. 眼镜请求计时约 30 秒，中间帧能否重置计时器不确定

- 现象一：只发一个中间帧（"请稍后"）、不发 done，约 30 秒后设备仍弹超时。
  → 单个中间帧不重置计时器。
- 现象二：每 8 秒持续推"…"中间帧时，设备未弹超时、会话保持存活，迟到答案
  正常显示（用户实测确认）。
- 结论：计时器更可能是"无帧活动计时"（约 30 秒收不到任何帧即超时），而非
  请求开始的死限；但无法排除"死限 + 恰好答案在限内到达"的解释。心跳按 8 秒
  间隔设计，无论哪种口径都安全。

## 4. 非终止帧会被语音播报拼接

- 现象：垫场帧"请稍后"与后续正式答案之间若无分隔，设备朗读时两句粘连。
- 设计影响：所有中间帧（心跳除外）与排队答案之间追加 `\n\n`；心跳使用省略号
  "…"（语音不朗读，HUD 只占一个字符）。

## 5. 唤醒词整句也会作为消息送达

- 现象：喊"龙虾助手"（含"呃/嗯"等语气词前缀）后，ASR 整句照样发给桥接层。
- 设计影响：适配器内置确定性唤醒词判定（去语气词/标点后仅剩唤醒词 ⇒ 静默关单），
  不询问模型。纯字符串规则，无 LLM 成本，不依赖任何宿主配置。

## 6. 网关状态语会污染语音输出

- 现象：Hermes 网关向平台推送的 "↪ 已重定向当前运行…"、"⏳ 正在处理—…"等
  内部状态通报，若原样到达眼镜会被朗读，用户感知为"乱播报"。
- 设计影响：`send()` 出站前按前缀（↪ / ⏳）吞掉；这些通报本身带
  `_interim_send` 标记，状态语过滤必须排在 interim 分支**之前**。

## 7. 打断发生在网关层，不在设备层

- 现象：上一轮运行中若把新消息交给网关（`handle_message`），网关默认
  interrupt 模式会掐断在途运行并发出重定向通知，眼镜丢答案。
- 设计影响：插话在**适配器层本地排队**，根本不交给网关，打断无从发生。
  不用宿主全局 `busy_input_mode: queue`——那是全平台生效的宿主配置，插件
  分享后别人环境没有该配置就不可用（插件自包含原则）。

## 8. 眼镜会话退出兜底

- 现象：会话以错误帧/超时异常结束时，眼镜固件自动退出智能体回主界面，需重新
  唤醒。
- 结论：固件行为，插件不可阻止；插件侧对策 = 消灭超时的产生条件（心跳 +
  不提前关单），重进体验靠唤醒词静默做到无缝。
